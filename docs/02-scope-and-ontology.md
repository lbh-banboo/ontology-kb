# 02 · 第一步：划域与最小可用本体

这一步决定后面所有事。做错的典型表现是：本体写了一千行，一张卡也没建。

## 2.1 先划域，不要先建类

**域（domain）是问题边界，不是分类学。** 划域的判据只有一条：

> 同一个域里的两张卡，有可能在**同一个问题**下同时被问到吗？

会 → 同域。不会 → 分开。分错了不要紧，域可以合并，类一旦建错会污染整棵树。

实操建议：域的数量控制在 **3–8 个**。示例库只有一个域（`咖啡冲煮域`）加一个跨域集合，
因为示例只需要证明「域字段能填、能分组」。

域的名字写进每张卡的 `domain` 字段，**一旦定了就不要再改名**——改名等于全部卡的字段失效。

## 2.2 只建 5 个实体类

L2 只有五类，这是刻意的克制：

| 类 | 判据（问自己） | 反例 |
|---|---|---|
| Concept | 它会被别的东西 `depends_on` 指向吗 | 「用户体验」——太大了，是话题不是概念 |
| Method | 能回答「怎么做」吗 | 「提高效率」——没有步骤，不是方法 |
| Tool | 有名字、能装能调吗 | 「AI 能力」——不是工具 |
| Scenario | 能回答「为谁解决什么、什么算成功」吗 | 「提效场景」——没有主语，不是场景 |
| Pattern | 在**不相邻的 ≥3 个领域**独立出现过吗 | 只在一个域出现——那是 Concept |

五类之外**一律不建**。想要「规则」「风险」「指标」这类类型，它们不是实体类，
是 §1 的**形态**字段 `obj_type`。混用会立刻导致关系校验失真：

```
# 错：把「规则」当实体类
type: Rule
constrains: ["[[X]]"]     # constrains 的源校验看 obj_type=规则，看 type 永远不通过

# 对
type: Concept
obj_type: 规则
constrains: ["[[X]]"]
```

## 2.3 只建 15 条关系

关系数量要少，因为**每条关系都自带一套语义约束，约束就是校验成本**。

结构类 7 条够描述骨架：`is_a` / `part_of` / `depends_on` / `implemented_by` / `applies_to` / `measured_by` / `produces`
治理与时态 5 条够管生命周期：`supersedes` / `conflicts_with` / `evidence_for` / `constrains` / `calibrated_by`
决策专属 3 条够记选择：`chooses` / `rejects` / `based_on`

### 选型口诀

拿不准用哪条时，按这个顺序试：

1. 是「一种」还是「一部分」？→ `is_a` / `part_of`
2. 少了它做不成？→ `depends_on`
3. 有具体东西实现了它？→ `implemented_by`
4. 限定在某个场景下才成立？→ `applies_to`
5. 有数可算？→ `measured_by`
6. 是硬性禁止/必须？→ `constrains`
7. 新旧两版？→ `supersedes`
8. 都不是 → **先不写**，写进正文，等想清楚了再补

第 8 条最重要。**宁可缺一条边，不要错一条边**——错的边会被下游查询当真，缺的边会显示为「无此关系」。

## 2.4 每条关系必须写清四件事

这是 §3.3 那张表存在的原因。缺任何一件，实现者就会各自发挥：

| 要写清 | 例（`measured_by`） | 不写会发生什么 |
|---|---|---|
| domain → range | 任意 → 指标 | 出现「指标 measured_by 规则」这种无意义边 |
| 是否传递 | 否 | 有人拿它做多跳，得出「A 的指标是 C」 |
| 反推是否成立 | 否 | 由「X 由 Y 度量」反推「Y 只度量 X」 |
| 前置条件 | 指标须写四口径 | 建了空指标卡，指标永远算不出来 |

`depends_on` 的传递=是、`implemented_by` 的传递=否，这个差别不是学术洁癖：
它直接决定 `kb.py impact` 会不会把影响面算成整个库。

## 2.5 验收判据（这一步做完的标志）

- [ ] 域数量 3–8 个，每个域能用一句话说清「什么问题的答案会落在这里」
- [ ] 实体类只用五类，没有第六类
- [ ] 关系只用 15 条，没有自定义谓词
- [ ] `vault/_schema/ontology.md` 里的关系数 == `vault/_kb/onto_rules.py` 里 `FORWARD` 的个数（CI 会断言）
- [ ] 能举出至少 3 张**真实**卡，说明它们该用哪条关系、为什么不用隔壁那条

最后一条是唯一的实质判据。做不出这一步，说明本体还停在纸上。

## 2.6 常见错误

| 错误 | 症状 | 修法 |
|---|---|---|
| 本体先于内容 | 写了 200 行词表，0 张卡 | 先手写 5 张卡，从卡里反推需要哪些关系 |
| 关系过细 | 出现 `has_similar_goal_to` 这类谓词 | 合并到 `is_a` 或写进正文 |
| 一个类装两种东西 | `Tool` 里既有软件又有方法论 | 方法论拆成 `Method`，`implemented_by` 连起来 |
| 域按部门划 | 域和团队一一对应 | 按「问题边界」划，不按组织结构划 |
| 追求完备 | 想一次覆盖所有领域 | 只做当前有真实问题的域，其余留空 |
