# 03 · 卡片规范：一张卡该长什么样

## 3.1 三个硬规则

1. **一张卡 = 一个概念**。文件名就是卡名（去 `.md`），改名等于断链。
2. **关系只写在 frontmatter**。正文怎么写都不进图。
3. **必填字段缺一不予入库**。不是靠人记，是靠 `kb.py check` 拦。

## 3.2 最小可用卡

```markdown
---
id: KB:coffee.method.Pour
type: Method
obj_type: 流程
domain: 咖啡冲煮域
modality: universal
definition: 分三段注水并各留一次排气间隙的做法；段与段之间靠液面下降判断节奏，不靠秒表
part_of: ["[[手冲咖啡]]"]
implemented_by: ["[[V60 滤杯]]"]
applies_to: ["[[新手首次手冲]]"]
anchors: ["示例数据：虚构，仅用于演示字段用法"]
evidence_level: C
valid_from: 2026-01-01
valid_until:
owner: kb-maintainers
---

## 定义

……
```

跑 `python3 vault/_kb/kb.py check`，这张卡应该 0 violation。

## 3.3 每个字段的坑

### `definition` —— 一句话，不能有模糊词

判据：**把这句话给一个不懂这个领域的人，他能判断「某个东西是不是它」吗？**

| 差 | 好 |
|---|---|
| 一种提高效率的方法 | 把人工逐步确认的动作替换为规则预判、仅异常回人的流程 |
| 较好的检索效果 | Top5 召回率 ≥ 80%（口径见指标卡） |
| 用户友好的界面 | 首屏无需滚动即可完成主任务的布局 |

「较好」「适当」「合理」「友好」这类词一出现，这张卡就永远无法验收。

### `type` / `obj_type` —— 两个字段，别混

`type` 是实体类（五类之一），`obj_type` 是形态（八类之一）。
最常见的错是把「规则」写进 `type`，导致 `constrains` 的源校验永远不过。
详见 [02](02-scope-and-ontology.md) §2.2。

### `modality` —— 决定这句话能被推广到多远

| 值 | 什么情况用 | 机器会强制什么 |
|---|---|---|
| `universal` | 对该类所有实例成立 | 无 |
| `possible` | 可能发生，但未发生 | 无，但输出时会标 `[possible]` |
| `instance` | 某个具体对象上已发生 | 必须写 `valid_from`；关系值必须写 `(对象，截至 YYYY-MM)` |

`instance` 的强制是最有用的：它逼你写出「对谁、什么时候」，
否则这句事实会在半年后被当成通用结论引用。

### `anchors` —— 必须能被另一个人独立定位

合格：`docs/02-scope-and-ontology.md §2.4`、`ISO 31000:2018 §5.4`、一个 URL、`书名 + 页码`。
不合格：`之前那篇笔记`、`会议讨论`、`老板口头说的`。

> 这条字段曾经要求过「稳定 media_id」，结果整库 anchors 全是笔记名，0 个合规，
> 而校验器只查「非空」——于是 `violation 0` 掩盖了「规范自己没生效」。
> 教训写进 [09](09-failure-modes.md) F7：**必填但无格式判据的字段，等于没有必填**。

### `owner` —— 写角色，不写私人称呼

`owner: kb-maintainers` 而不是 `owner: 张三`。
原因是这个字段会被外部读者看到，而外部读者不需要知道你的内部称呼。
一行 `owner: 张三` × 几十张卡，就是一个很小的仓库里几十处私人信息。

### `valid_from` / `valid_until` —— 会失效的东西必须带时间

判据：**这条知识半年后还成立吗？**

- 会（如「is_a 要求同类」）→ `valid_until` 留空，视为长期有效但需复核
- 不会（如「某系统截至 2026-09 的能力」）→ 必须写 `valid_until`，并在被替代时登记 `supersedes`

## 3.4 关系字段的六种写法

| 场景 | 写法 | 说明 |
|---|---|---|
| 指向已建卡 | `"[[卡名]]"` | 正常边 |
| 指向未建卡 | `"卡名"`（纯文本） | 占位节点，warn 不 violation |
| 可能发生 | `"[possible] [[卡名]]"` | 输出时可见 |
| 实例事实 | `"[instance] [[卡名]] (对象，截至 2026-09)"` | 缺时间范围判 violation |
| 带说明 | `"[[卡名]] (说明文字)"` | 说明进 qualifier |
| 带理由 | `"[[卡名]] | 理由"` | `rejects` / `conflicts_with` **必须**带，否则 violation |

⚠️ 列表必须是 **JSON 双引号写法**，不能写 YAML 单引号：
`["[[A]]", "[[B]]"]` ✅ ｜ `['[[A]]', '[[B]]']` ❌ 解析直接报错。

这是刻意的——本仓库解析 frontmatter 不引入任何第三方依赖（见 README「为什么零依赖」），
只支持 `key: 值` 和 `key: ["a","b"]` 两种形态。省掉一个依赖，换来的是「格式只有一个正确答案」。

## 3.5 正文写什么

正文**不参与推理**，但它决定这张卡有没有用。建议三段：

```markdown
## 定义
把这个概念讲清楚，允许比 frontmatter 的 definition 长。

## 为什么 / 边界
它为什么成立、在什么条件下不成立、容易和什么混淆。

## 相关
[[提及]] 写在这里只供人读。想让它进图，把关系写进 frontmatter。
```

正文里可以随便写 `[[链接]]`，**都不会进图**。这一点是最大的混淆源，单独一篇讲：[04](04-body-vs-relation.md)。

## 3.6 一张卡写完的自检

- [ ] `definition` 里没有「较好/适当/合理/友好」这类词
- [ ] `type` 是五类之一，`obj_type` 是八类之一（Pattern 免填）
- [ ] 至少有一条 typed 关系，或者被别的卡指向
- [ ] `anchors` 里任意一条，能让别人独立找到原文
- [ ] 会失效的内容写了 `valid_until`
- [ ] `owner` 是角色不是私人称呼
- [ ] `kb.py check` 这张卡 0 violation

前六条靠人，第七条靠机器。**只做第七条的，前六条一定会烂。**
