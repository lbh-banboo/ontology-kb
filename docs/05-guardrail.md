# 05 · 守门：把校验放在提交前

## 5.1 一句话

**校验放在提交后，等于烂数据已经进了历史。** 放在提交前，它才拦得住。

## 5.2 三道拦截

`tools/pre-commit` 只做三件事，每件事对应一种真实失效：

| # | 拦截什么 | 为什么必须在这里拦 |
|---|---|---|
| 1 | 疑似云盘冲突副本（`xxx 2.md`） | 副本进版本后，关系图凭空多一张同名卡，且**不报错**——只是多了一个节点 |
| 2 | `kb.py check` 有 violation | 缺必填字段、domain/range 违规、环。这些一旦入历史，后续所有查询都建立在坏数据上 |
| 3 | `kb.py test` 未全过 | 关系推理行为被改坏。改一张卡可能让 5 个查询结果变空，而 check 完全发现不了 |

注意第 2 条只拦 **violation**，**warn 放行**。这不是偷懒，是刻意的：
存量欠账（未建卡占位、指标口径缺失）如果也拦，第一天就堵死所有提交，最后所有人 `--no-verify`。

> **拦截阈值的设计原则：拦「新增破坏」，放「存量欠账」。**
> 存量欠账用清单管理（谁、哪条、为什么保留），不用钩子管理。

## 5.3 安装

```bash
bash tools/install-hooks.sh
```

它做两件事：

```bash
chmod +x tools/pre-commit
git config core.hooksPath tools      # 钩子目录指向 tools/
```

验证：

```bash
git commit --allow-empty -m "verify hook"
# 期望输出：✅ 守门通过：violation 0 ｜ warn N ｜ 断言 10/10 PASS
```

卸载：`git config --unset core.hooksPath`。

## 5.4 为什么用 `core.hooksPath` 而不是 `.git/hooks/`

`.git/hooks/` 不进版本库。你在本机装好了，同事 clone 下来什么都没有，
于是「守门」变成「只有一个人有守门」。

`core.hooksPath` 指向版本库里的目录，钩子本身也受版本管理——
它像代码一样被 review、被改、被回滚。代价是每个 clone 都要手动跑一次 `install-hooks.sh`（因为 `core.hooksPath` 是本地配置）。

> 想省掉这一步，可以在 CI 里再跑一遍同样的校验。
> 但**不要**指望 CI 替代钩子：钩子拦的是「提交」，CI 拦的是「推送」，中间那段是你的本地历史。

## 5.5 两个必须写进注释的坑

这不是洁癖。这两个坑都真实发生过，第二个还让坏数据进过一次提交。

### 坑一：`core.quotepath` 让 grep 永远不匹配

Git 默认把非 ASCII 路径转义成 `"\344\270\255\346\226\207 2.md"` 这种形式，行尾多一个引号。
于是 `grep -E ' [2-9]\.md$'` 匹配不到任何东西——**包括真的副本卡**。

正确做法：用 Python 按 basename 判，不依赖路径是否被转义。

```python
bad = [p for p in paths if re.search(r" [2-9]\.md$", p.rsplit("/", 1)[-1])]
```

### 坑二：PATH 里的 Grep 不等于系统 grep

各种工具链会在 PATH 前面塞 shim，行为可能和系统 grep 不同（有的不认 `-E`，有的改了输出格式）。
钩子里能用 Python 就别用外部命令。

## 5.6 绕过与补跑

```bash
git commit --no-verify -m "紧急提交"
python3 vault/_kb/kb.py check     # 提交后立刻补跑
```

**绕过改的是钩子，不改原则。** 原则是「进历史的状态必须校验过」，
所以补跑之后如果有 violation，应该在下一个提交里修掉，而不是等它烂在那里。

想彻底禁止绕过？钩子里没有可靠办法（`--no-verify` 是客户端行为）。
可靠的办法是服务端 CI + 受保护分支——但那已经不是「个人知识库」的花费了。

## 5.7 钩子跑得慢怎么办

当前实现是全量检查（几十张卡毫秒级）。到几千张卡时会变慢，按这个顺序优化：

1. 先测：`time python3 vault/_kb/kb.py check`。没超过 2 秒就别优化。
2. 只查改动卡：`git diff --cached --name-only` 拿路径，只校验这些卡 + 它们的直接邻居。
3. 缓存图快照：按文件 mtime+size 做键，未变则复用上次解析结果。

第 2 条有个陷阱：**只查改动卡会漏掉「被改动卡指向的那张卡的约束」**，
所以至少要带上直接邻居。这个陷阱在小库上测不出来，到几千张卡才会暴露。

## 5.8 验收判据

- [ ] `git commit --allow-empty` 能打印「守门通过」
- [ ] 故意把一张卡的 `type` 改成 `Rule` → 提交被拒，且错误行指出是哪张卡
- [ ] 故意建一个 `测试 2.md` → 提交被拒，且提示「疑似冲突副本」
- [ ] 故意改坏 `tests.json` 里一条 expect → 提交被拒，打印 `[FAIL]` 那一行
- [ ] 恢复上述三处改动后，提交通过

后四条才是验收。**一个从没拦住过东西的钩子，等于没有钩子。**
