# 09 · 15 条失败模式

按「症状 → 根因 → 修法」写。全部是真实踩过的，编号可被 issue 直接引用。

---

## F1 · 关系数量三个地方三个数

**症状**：规范标题写「11 个关系」，表格列了 7+5=12 行，代码白名单里 12 个，决策层另加 3 个但没改标题。四个数字并存。

**根因**：数字是手写的，不是算出来的。手写数字只要没人核对，就一定会漂。

**修法**：让 CI 断言「文档里声明的数 == 代码里 `FORWARD` 的长度」。
断言不了的部分（比如「结构类/治理类怎么分」）就在同一句话里写清算式：`7 + 5 = 12`。

**可复用判据**：任何写进文档的数量，必须能用一个命令重算出来。

---

## F2 · 两套规则实现并存，旧的那套还在被调用

**症状**：新实现 `v0.3`，旧实现 `v0.2` 标着「保留不动」，注释写「改本体时两边同步改」。实际有 5 个脚本仍 `import` 旧版。

**根因**：「保留旧版」的动机通常是怕破坏旧流程，但**没有失效标记的保留 = 双真相源**。

**修法**：旧实现要么加 `DEPRECATED` 抬头 + 明确「只服务 X 旧轨道」，要么合并。
「两边同步改」这种承诺没有机器保障，等于没有。

**可复用判据**：`grep -r "import onto_rules"` 只能有一个来源。多于一个就是 F2。

---

## F3 · 用 LLM 自动抽关系当主力

**症状**：抽了 200 条边，图看起来很密，但问「改 A 会影响谁」出来一堆无关结果，人逐渐不信查询。

**根因**：见 [01](01-why-not-vector-first.md) 的三个结构性失效（未知关系静默丢弃、无法判对错、语义约束无法自动满足）。

**修法**：LLM 只做**起草**，人做**准入**。每条自动抽的边必须过三道判据（谓词唯一、方向明确、会被查询用到）。

**可复用判据**：抽出的边若无法写成一条 `kb.py test` 断言，就不该进图。

---

## F4 · 校验器只查「字段非空」，不查「格式对不对」

**症状**：规范要求 `anchors` 是「稳定 media_id」，实测全库 anchors 全是笔记名，0 个合规；而 `check` 报 `violation 0`。

**根因**：必填字段的实现只做了 `if not fm.get(k)`。**「非空」和「合规」是两件事。**

**修法**：二选一——真落地格式判据，或者放宽容许的口径并同步改文档。
最糟的是现在这样：规范说 A，校验只查 not-A，于是绿灯骗人。

**可复用判据**：每个「必填」字段，必须在校验器里有一行判据；没有就删掉这项必填。

---

## F5 · 必填字段在配置里声明了，但代码从没引用

**症状**：配置区有 `CHECKLIST_ITEMS`、`CARD_TS` 这类常量，交付文档也写「已校验该表」，但删掉清单项、改坏时间戳，校验依然全绿。

**根因**：常量写了，判据没接。

**修法**：配置区每个常量都必须能指出「哪一行判据在用它」。指不出来 = 声称验了但根本没跑。

**可复用判据**：删掉这个常量，判据会变红吗？不会就是 F5。

---

## F6 · 判据是恒真式

**症状**：`PASS 31 / FAIL 0`，看着很健康；但注入一个明显错误，仍然 `PASS 31 / FAIL 0`。

**根因**：判据写成了「不变量」而不是「可证伪的断言」。典型：`None == None` 静默全绿；
`xref_stream(page.xref)` 两边都返回 `None`，于是「跨文档一致」永远成立。

**修法**：**先做变异测试**。注入变异，要求「最终结论翻红 **且** 被变异的那条判据精确翻红」。
只验检测器返回值不够，要验最终结论。

**可复用判据**：判据写完先问一句：**什么情况下它会红？** 答不出来就是恒真式。

> 恒真比恒假更危险。恒假你会去查，恒真你会信。

---

## F7 · 判据跑在已经被过滤的数据上

**症状**：判据检查「产物里没有空段」，但输入列表在传进判据前已经 `[x for x in segs if x.strip()]` 过滤过。注入空段也不报警。

**根因**：判据和被测对象不是同一份数据。

**修法**：判据跑**未过滤的原始数据**；另外补一条「产物段数 == 原始段数」防静默丢段。

**可复用判据**：判据的入参，必须是磁盘上那份文件，不是内存里加工过的版本。

---

## F8 · 判据假设了错误的数据格式

**症状**：拿 45 秒聚合段文件（带 `[mm:ss-mm:ss]` 段头）去和纯文本流比，必然差 510 字，误判「文档漏句」。

**根因**：没先看清文件真实格式就写比对。

**修法**：比对前先 `head` 看格式，按**该文件真实格式**剥掉结构标记。

**可复用判据**：复核报 FAIL 时，第一个要怀疑的是**自己的口径**，不是产物。

---

## F9 · `core.quotepath` 让冲突副本检测静默失效

**症状**：钩子里用 `grep -E ' [2-9]\.md$'` 检测云盘副本，中文路径下永远匹配不到。副本卡真的进过一次提交。

**根因**：Git 默认把非 ASCII 路径转义加引号（`"\344\270\255\346\226\207 2.md"`），行尾多一个 `"`。

**修法**：用 Python 按 basename 判：`re.search(r" [2-9]\.md$", path.rsplit("/", 1)[-1])`。

**可复用判据**：建一个 `测试 2.md` 提交一次。拦不住就是 F9。

## F10 · 拦截阈值定错：全拦导致所有人绕过

**症状**：钩子把 warn 也拦，第一天就堵死所有提交；一周后所有提交都带 `--no-verify`，守门名存实亡。

**根因**：把「存量欠账」和「新增破坏」放在同一档拦截。

**修法**：**拦新增破坏（violation），放存量欠账（warn）**。欠账用清单管理：谁、哪条、为什么保留、什么时候还。

**可复用判据**：连续 10 次提交里 `--no-verify` 的次数。大于 0 就说明阈值定错了。

## F11 · 用均值做判定，被暗角/异常值污染

**症状**：判定「背景色是否一致」用全局平均色，但图四角亮度 57、中心 195，均值落在中间，与任何真实背景都不等。

**根因**：均值对分布形状不敏感。

**修法**：背景/主色类判定一律用**量化众数**，不用均值；边缘采样要先排除主体区。

**可复用判据**：换一张极端光照的样本，结论是否仍然成立？

---

## F12 · 一个变量背两个口径

**症状**：`DUR = max(end)` 既当「音频总长」又当「末句终点」。差 1.6 秒尾部静音，于是误判文档写的时长错了。

**根因**：同名变量承载两个语义。

**修法**：口径一拆二（`DUR_AUDIO` / `DUR_LAST_SEG`），**变量名自带口径**。

**可复用判据**：这个变量能被两句话描述吗？能就有 F12。

---

## F13 · 覆盖旧的评测轮次

**症状**：新一轮评测直接覆盖上一轮目录，于是「上一轮到底差在哪」永久丢失，也无法证明「这次没偷偷改题」。

**根因**：图省事。

**修法**：**每轮一个新目录，永不覆盖**。旧轮次目录里写一句「不得修改本目录」。

**可复用判据**：`ls` 能看到全部历史轮次，且每轮有独立结论文件。

---

## F14 · 把 `possible` 当 `instance` 用

**症状**：写「换 embedding 模型会导致语义错位」（possible），被下游当成「已经发生过」（instance）引用，进而推出「所以现在不能换」。

**根因**：中文里两者都长得像陈述句。模态只写在 frontmatter，正文读起来没区别。

**修法**：`instance` 强制 `valid_from` 与 `(对象，截至 YYYY-MM)`；输出时带 `[possible]` / `[instance]` 标记；
正文里凡陈述可能性的句子，开头写「可能」。

**可复用判据**：`kb.py constraints <卡>` 的输出里，模态标记是否可见。

---

## F15 · 凭据与绝对路径进了 Git 历史

**症状**：项目根目录两个未跟踪文件里有明文 API key 和账号 ID；已提交的 3 个脚本里写死 `/Users/<name>/...`；历史提交信息含私有仓库地址。

**根因**：`git add .` 是常态，`.gitignore` 是黑名单，漏一个就进历史。

**修法**：

1. `.gitignore` 改成**白名单**（默认全忽略，显式允许）
2. 敏感串用 `git grep` 在 CI 里跑成 0 命中
3. 已经进了历史的：**不要 force push 改历史**，另开一个干净仓库做首提交

**可复用判据**：`git log --all -p | grep -c '<敏感串>'` == 0。
新仓库还要多一条：首个提交是唯一提交（`git rev-list --count HEAD == 1`）。

## 使用方式

遇到新问题先在这里找同类。**加一条新失败模式的标准是：它能写出一句可执行的判据。**
写不出判据的，是抱怨，不是失败模式。
