# 04 · 正文提及与 typed 关系：最大的混淆源

## 4.1 一句话

同一串 `[[卡名]]`，写在 frontmatter 里是**关系**，写在正文里是**提及**。
关系进图可推理，提及只供人读。

```markdown
---
depends_on: ["[[萃取率]]"]      # ← 关系：kb.py ask 查得到
---

正文提到 [[萃取率]] 时……        # ← 提及：kb.py ask 查不到
```

## 4.2 为什么不做「正文里的链接也算关系」

听起来更省事，实际上会毁掉这套方案的三条根基：

| 后果 | 说明 |
|---|---|
| 关系数量不可控 | 一篇文章提到十个概念就产生十条边，其中九条是修辞 |
| 无法表达语义 | `[[A]]` 是依赖？是替代？是反驳？正文链接不带谓词 |
| 无法判定方向 | 「A 依赖 B」和「B 依赖 A」在正文里长得同一句话 |

第三条最致命：一旦方向要猜，图上所有影响面分析都不可信。

## 4.3 什么时候该升级成关系

一条提及值得升级成 typed 关系，必须同时满足：

1. **能被下游查询用到**：有人会问「谁依赖它 / 它约束谁 / 谁替代了它」
2. **谓词唯一**：能明确说是 15 条里的哪一条，而不是「有关系」
3. **方向明确**：能说清 A→B 还是 B→A

只满足第 3 条就升级，会造出一堆没法用的边。

## 4.4 一个反直觉的结论：少写关系更好

假设有 20 条提及，其中只有 3 条能过上面三道判据。

- 写 20 条：图看起来很密，但 17 条是噪声。之后每一次 `impact` 查询都会返回一堆无关结果，
  人会逐渐不信查询结果——**这比没图更糟**。
- 写 3 条：图稀疏，但每条都能用。缺的边在查询时显示「（库内无此关系登记）」，
  这个提示本身就在告诉你「这里该补一条边」。

> 稀疏且正确 ＞ 稠密且含糊。
> 判断标准：**`kb.py impact` 的输出，你敢不敢直接拿去做决策？**

## 4.5 一个具体例子

示例库的案例卡 `2026-03 首次手冲记录`：

```markdown
---
evidence_for: ["[[注水手法]]"]        # 唯一登记的 typed 关系
---

成品偏酸、薄 → 按 [[金杯准则]] 的处置表，先判「萃取不足」，动研磨而不是加水。
```

正文提到了 `金杯准则`，但它**不是**关系——因为「按它处置」不是一个谓词：
是 `depends_on`？是 `constrains`？还是 `based_on`？说不清就不写。

验证：

```bash
$ python3 vault/_kb/kb.py ask "2026-03 首次手冲记录"
## 依赖链：2026-03 首次手冲记录 `KB:coffee.case.FirstRecord`
（库内无此关系登记）
```

`（库内无此关系登记）` 不是 bug，是这套设计的核心反馈信号。

## 4.6 迁移老笔记的做法

存量笔记一般全是正文链接。不要批量转换，按这个顺序做：

1. **先挑 10 张最常被问到的卡**，手工补 typed 关系，边补边判断谓词
2. 跑 `kb.py impact <卡>`，看输出是否符合你的直觉
3. 不符合 → 是关系写错了，不是工具错了，改关系
4. 符合了，再挑下一批 10 张

一次全量转换的结果几乎一定是：300 条边，你一条都不敢信。

## 4.7 检查你是否踩了这个坑

```bash
# 占位节点很多 → 说明大量关系目标没建卡，或谓词写得含糊
python3 vault/_kb/kb.py stats

# 某张卡输出「无此关系登记」，但你确定它有关联 → 关系还写在正文里
python3 vault/_kb/kb.py ask <卡名>
```

`stats` 里 `未建卡目标` 的数量长期超过卡片数，通常意味着两张情况之一：
你的领域本来就很碎（正常），或者你在用「纯文本关系」逃避做判断（要修）。
