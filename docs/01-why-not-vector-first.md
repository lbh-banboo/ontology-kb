# 01 · 为什么不先上向量检索

## 起点：一个很常见的失败路径

大多数个人知识库是这样长起来的：

1. 笔记越攒越多，找不到 → 上全文搜索
2. 全文搜索只能命中字面，问「这两个方案什么关系」搜不到 → 上向量检索
3. 向量检索只能返回「看起来像的段落」，答不了「谁替代了谁」→ 上 GraphRAG
4. GraphRAG 自动抽关系，抽出来的边对不对没人能验 → 加上 LLM 判断
5. 判断结果不稳定，无法回归 → 加更多层，成本继续涨

问题不在第 3 步选错了工具，而在于**第 1 步就问错了问题**：
「我找不到」常常不是检索问题，是**知识之间的联系从来没有被显式记录过**。

## 关键区别：检索 vs 数据

| | 检索路径 | 数据路径 |
|---|---|---|
| 关系存在哪 | 隐式：向量空间里的邻近性 | 显式：frontmatter 里的 `depends_on: ["[[X]]"]` |
| 怎么得到答案 | 相似度召回 + 模型生成 | 图上遍历，输出已登记的边 |
| 对不对怎么验 | 只能看生成结果像不像 | 断言 `ask A depends_on` 必须包含 B |
| 同一个问题问两次 | 可能不同答案 | 一定相同 |
| 出错时能否定位 | 不能，向量没有可读结构 | 能，指到具体那张卡的哪个字段 |

**只有第二列能做回归测试。** 不能做回归的东西，就不可能在规模变大后保持正确——
你只是在赌它这次没变坏。

## 反面教材：自动关系抽取的三个具体失效

这里的判断不是「LLM 抽关系效果不好」，而是三个**结构性**问题：

### F-a 未知关系被静默丢弃

多数抽取管线在遇到词表外的关系谓词时，会走「映射到最近邻」或者「丢弃」两条路。
丢弃这条路上，日志里通常只是一行 debug。结果是：你以为抽了 200 条边，实际入图 140 条，
**剩下 60 条去了哪里，没有任何机制告诉你**。

> 修法不是「加上日志」，而是让非法关系**直接失败**（本仓库的做法：`check_edge` 判 violation，提交前拦截）。

### F-b 抽出来的边无法判对错

给定正文「V60 流速快，所以更适合训练手法」，抽成 `V60 →applies_to→ 训练手法` 是对的吗？
严格说不成立：适合训练的是**这个组合**（快流速 + 可观察），不是滤杯本身。
这类边界错误在自然语言里无处不在，而**没有 ground truth 就无法标注**，没有标注就无法度量改进。

### F-c 关系方向与语义约束无法自动满足

`applies_to` 的目标必须是场景，`constrains` 的源必须是规则。
人写的时候会被校验器拦下来，抽取器不会——它只会输出一个看起来合理的谓词。
于是图里开始出现「规则 applies_to 规则」这种结构上合法、语义上无意义的三元组，
而所有下游查询都建立在它上面。

## 那这套方案不要向量检索吗

不。位置不同：

| 层级 | 该用什么 | 判据 |
|---|---|---|
| 「我知道有这张卡，帮我找它」 | 向量/关键词检索都行 | 找到即可，不需要推理 |
| 「这两张卡什么关系」 | **图遍历** | 关系已在 frontmatter，不需要猜 |
| 「给我一段可能相关的原文」 | 向量检索 | 召回即可，下游人工判断 |
| 「这个结论有没有依据」 | 图遍历 + anchors | 必须能指到具体来源 |

**向量检索做召回的入口，图遍历做关系的答案。** 反过来的顺序，就会掉进上面那条失败路径。

## 什么时候该用这套

适合：

- 知识的价值主要在**关系**（方案演进、规则约束、决策依据、依赖顺序）
- 需要回答「谁替代了谁」「改 A 会影响谁」
- 内容规模在千条量级，人还能审完
- 对「答案可复现」有要求

不适合：

- 主要需求是「找一段我读过的原文」——全文搜索足够
- 无人维护、也不打算维护的长尾语料
- 需要覆盖百万级条目的开放域问答

## 一条判据

在决定上任何检索/图谱系统之前，先回答一个问题：

> **我要问的十个问题里，有几个是「找原文」，几个是「找关系」？**

如果十个都是找原文，别建本体，装个好用的全文搜索就行。
如果有一半是找关系，那这些关系现在存在哪里？如果答案是「在我脑子里」，
那么**先把它们写下来**，比选任何引擎都重要。
