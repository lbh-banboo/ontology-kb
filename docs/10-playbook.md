# 10 · Playbook：从零到跑起来

12 步。每步都有**验收判据**，判据没过不要进下一步——
这套方法的失败几乎都是「本体没定就先建了 200 张卡」这类顺序错误。

总投入：**第 0–5 步约 2 小时**，第 6–8 步每张卡 3–5 分钟，第 9–11 步一次性半天。
100 张卡以下的库，前六步当天能做完。

---

## 第 0 步 · 先回答一个问题

> 我要问的十个问题里，有几个是「找原文」，几个是「找关系」？

全部是找原文 → 别做这套，装个好用的全文搜索。
有一半是找关系 → 继续。

**验收**：你能写下 5 个**具体的**找关系类问题。
写不出来，说明关系还没到值得建模的程度。

---

## 第 1 步 · 划域

列出当前所有知识内容，按「什么样的**同一个问题**会把它们同时问到」分组。

**验收**：

- [ ] 3–8 个域，每个域能用一句话说清「什么问题会落在这里」
- [ ] 没有「其他」「杂项」这类垃圾桶域（有就说明分组没做完）
- [ ] 每个域至少有 5 条真实内容（不足 5 条的先不做）

⚠️ 常见错误：按部门/职能划域。要按**问题边界**划。

---

## 第 2 步 · 定最小本体

复制 `vault/_schema/ontology.md`，只改三处：

1. §4 的 `<域>` 取值（你的域名）
2. §2 如果确有必要，增删实体类（**默认不改**）
3. §3 如果确有必要，增删关系（**默认不改**）

**验收**：

- [ ] 关系总数 = 结构 7 + 治理 5 + 决策 3 = 15，且与 `vault/_kb/onto_rules.py` 的 `FORWARD` 长度一致
- [ ] 每条关系在 §3.3 的表里有完整一行（domain/range、传递、反推、模态、前置）
- [ ] 你举不出「需要第 16 条关系」的例子

⚠️ 这一步骤最容易过度设计。判断标准：**能不能用 5 张卡证明某条关系是多余的？** 能就删。

---

## 第 3 步 · 手写 5 张卡

不要写脚本批量导。手写，因为手写过程会暴露规范问题。

选 5 张覆盖不同形态的：一个概念、一个方法、一个工具、一个场景、一条规则。

**验收**：

- [ ] 5 张卡 `kb.py check` 全部 0 violation
- [ ] 至少有一条关系是「你以为要写 A，实际写了 B」——这个过程必须发生，没发生说明你没认真选
- [ ] 每张卡 `anchors` 里有一条能被另一个人独立定位

```bash
python3 vault/_kb/kb.py check
```

---

## 第 4 步 · 定 frontmatter 的格式纪律

三件事定死，写进 `CONTRIBUTING.md`：

1. 列表必须 JSON 双引号写法：`["[[A]]", "[[B]]"]`
2. 文件名 = 卡名，改名必须全局替换
3. 关系只写在 frontmatter

**验收**：

- [ ] 故意写一个 YAML 单引号列表，`check` 报解析错
- [ ] 故意在正文写 `[[链接]]`，`kb.py ask` 查不到它

第二条是最重要的验收。很多人以为「正文链接也算」，试一次就明白了。

---

## 第 5 步 · 装守门

```bash
bash tools/install-hooks.sh
git commit --allow-empty -m "verify hook"
```

**验收**（四条都要过，见 [05](05-guardrail.md) §5.8）：

- [ ] 空提交打印「守门通过」
- [ ] 把 `type` 改成 `Rule` → 提交被拒
- [ ] 建 `测试 2.md` → 提交被拒（提示冲突副本）
- [ ] 改坏一条 `tests.json` 的 expect → 提交被拒（打印 `[FAIL]`）

**一个从没拦住过东西的钩子等于没有钩子。** 这四条不做，后面所有校验都是装饰。

---

## 第 6 步 · 批量导入存量（每次 10 张）

禁止全量转换。一次 10 张，每批做完跑一次 `impact`：

```bash
python3 vault/_kb/kb.py impact <刚建的一张卡>
```

**验收**：

- [ ] 每批 `check` 0 violation
- [ ] `impact` 输出与你的直觉一致；不一致就改关系，别改工具
- [ ] 一批里平均不超过 2 条「拿不准谓词」的边（多于 2 条说明这批选题太杂）

⚠️ 存量笔记的正文链接**不要自动转成关系**。按 [04](04-body-vs-relation.md) §4.3 的三道判据逐条判断。

---

## 第 7 步 · 补生命周期

对每张卡问：**这条知识半年后还成立吗？**

- 会 → `valid_until` 留空
- 不会 → 写 `valid_until`，将来被替代时登记 `supersedes`

**验收**：

- [ ] 所有 `instance` 卡都有 `valid_from`，关系值带 `(对象，截至 YYYY-MM)`
- [ ] 所有决策卡都有 `review_at` 且不是过去时间
- [ ] `kb.py check | grep -E "review_at|valid_until"` 的输出能逐条说清「复核 / 保留 / 补替代」

---

## 第 8 步 · 写正文

frontmatter 保证「能被机器查」，正文保证「人读得懂」。三段式：

```markdown
## 定义
## 为什么 / 边界
## 相关
```

**验收**：把一张卡给一个不懂这个领域的人看，他能说出「什么时候该找这张卡」。

---

## 第 9 步 · 建评测题集

首批 100–200 条，正负样本都要有。详见 [07](07-evaluation.md)。

**验收**：

- [ ] ≥ 100 条，其中负样本 ≥ 20%
- [ ] 每条有 `cmd` / `card` / `expect`；负样本有 `forbid`
- [ ] `kb.py test` 能跑完并给出 `N/M PASS`
- [ ] 有改题记录表（区分「改判分 / 修题 / 前提变更」）

---

## 第 10 步 · 定同步与备份

```bash
python3 tools/sync_icloud.py --mirror   # 云盘单向镜像，冲突即停
git remote add origin <你的远端>
git push -u origin main
```

**验收**：

- [ ] 只有一处目录接受写入
- [ ] 云端变过时镜像**停住**而不是覆盖（手动造一个改动试）
- [ ] 远端 README 写明「禁止网页端直接编辑」
- [ ] 有一个**验证过能恢复**的离线副本（`git clone` 到临时目录跑 `kb.py check`）

---

## 第 11 步 · 写 README，如实标注状态

必须写清四件事：

1. 这是什么（TBox + ABox + 零依赖 CLI）
2. 怎么跑（三条命令）
3. 当前评测状态（**未达标就写未达标**）
4. 不包含什么（个人数据、第三方源码、内部文档）

**验收**：一个陌生人 clone 下来，不看别的文档，能在 README 里跑通 check 和 test。

---

## 之后：日常循环

每周：

```bash
python3 vault/_kb/kb.py check          # 有没有新增 violation
python3 vault/_kb/kb.py test           # 关系有没有被改坏
python3 vault/_kb/kb.py stats          # 卡数 / 占位 / 边数 的趋势
```

每月：

```bash
python3 vault/_kb/kb.py check | grep review_at      # 该复核的决策
python3 vault/_kb/kb.py check | grep valid_until    # 该补替代的过期内容
```

三条命令的输出就是待办。**没有输出的月份不要伪造待办。**

---

## 顺序错了会怎样

| 跳过 | 后果 |
|---|---|
| 跳过第 0 步 | 建了一堆关系，发现没人查 |
| 跳过第 1 步 | 域划分反复改，全部卡的 `domain` 字段失效 |
| 跳过第 5 步 | 前面积累的错误全部进历史，之后每次查询都建立在坏数据上 |
| 跳过第 9 步 | 无法知道改动是变好还是变坏，只能靠感觉 |
| 跳过第 11 步 | 三个月后你自己也忘了这套东西怎么用 |
